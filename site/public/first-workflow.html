02/First workflow

A first workflow, from a real run

One small project taken through a full DevFlow cycle. Every block below is the real output of the command above it, run on 9 November 2026. Nothing was retried to get a cleaner result: the run found a real bug, stopped at three real gates, and ended blocked on a remote that isn't GitHub. All of it is shown.

··The run at a glance

Plans rejected
Twice. Once for a test check that could not fail, once for a check that depended on work a later task would do.
Gaps found
One real bug that all 14 of the executor's tests missed, found by the verifier.
Abstentions
Two unsettled requirements and one timing taken on a loaded machine. None was certified. Each went to a person.
Human gates
Three, each with its options spelled out, each answer written to DECISIONS.md.
Review
Seven lenses, two rounds, one blocking finding left for a person with the cost of each option measured.
Merges
None. DevFlow never merges. On GitHub it would have opened the PR and handed the merge to a person.

Under /goal or /loop, each of these gates stops the run the same way, because gates never auto-proceed. To drive a project that way: /goal FLOW says DONE, GATE, or BLOCKED, or stop after 40 turns, then /flow-next.

00The project

A tiny Python command-line tool, wordfreq, that prints the most frequent words in a text file. It starts as an empty git repository with one empty commit and an origin remote, which here is a local bare repository rather than GitHub.

/flow-new
Writes requirements and a roadmap.
/flow-plan 1
Writes and checks the phase's plan.
/flow-execute 1
Builds it, then an independent verifier checks it.
/flow-next
Takes one step on its own, and stops at a gate.
/flow-pr
Reviews the diff and opens a pull request.

01Initialize with /flow-new

Given a description and --auto, /flow-new skips its question round, picks the lite tier because the project is small and deploys nothing, writes .planning/ on a new flow/wordfreq branch, commits, and pushes. Note what it does with what you did not say: every default it picked is listed as an assumption for you to check, and the one real open question is marked rather than guessed.

02Orient with /flow-status

Run it in any session, at any time. It reads .planning/ and prints the exact next command.

03Plan with /flow-plan 1

The planner writes the plan, then a plan-checker tries to reject it. Here it found two blocking problems, including a test check that would have passed even when the tests failed. The planner revised the plan once and it passed.

04Execute with /flow-execute 1

An executor built the tool and its 14 tests, all passing. Then a separate verifier checked the phase against its must-haves and found a gap the tests did not cover: some bad paths still crash with a traceback. It also refused to certify the two behaviours the requirements never settled, and handed them to a person.

05Check in with /flow-status

Status reads the verifier's report and routes to the gap replan. It also noticed two planning files that disagreed with each other, and reported them instead of quietly fixing them.

06Hand over to /flow-next

/flow-next takes exactly one step. Under /goal or /loop it would be called again and again. Here the next step needed a decision only a person can make, so it raised a gate with numbered options and stopped. A loop would have stopped here too.

07Answer the gate

The answer goes in as plain words after the command. DevFlow writes the question and the answer word for word to DECISIONS.md, updates the requirements, and plans the gap fix. The plan-checker rejected the first gap plan too.

08Fix the gap with /flow-next

With the gate answered, /flow-next executes the gap plan. The traceback is fixed and every must-have passes except one: the 10 MB speed target. The verifier's timings came out over the limit, but the machine was heavily loaded, so they prove nothing either way. It did not pass the check and did not fail it. It asked a person to time it.

09Do the human check, then /flow-verify 1

The operator timed the tool by hand and passed the numbers in, unedited, including the slow run and the fact that the machine was not idle. Accepting the target was the operator's call, and the verifier records it with its caveats rather than as a clean pass.

10Review and open the PR with /flow-pr

Seven reviewers read the outgoing diff in parallel, each through one lens. DevFlow fixed what it could, with a regression test for each fix, and re-reviewed. One blocking finding remained that it would not decide alone: fixing it changes a requirement and slows the tool enough to threaten the speed target. So it stopped before pushing and laid out the options.

11Answer, push, and an honest stop

The operator chose to defer the finding. DevFlow records the decision, updates the requirements and the PR body, and pushes the branch. Then it stops: this scratch project's origin is a local bare repository, not GitHub, so there is nothing to open a pull request against. It says so and reports BLOCKED instead of inventing a URL. On a GitHub remote, this step opens the PR, ready for review.

··How these were captured

Each command ran headless, in a scratch repository created with mktemp, loading DevFlow from a checkout of this repository for that one session:

claude --plugin-dir <devflow-checkout>/plugins/devflow \
  --setting-sources user \
  --settings '{"enabledPlugins":{"devflow@devflow":false}}' \
  --permission-mode bypassPermissions \
  -p "<command>" < /dev/null

The --settings flag switches off the installed copy for that session so the checkout's skills answer, which is why commands read /devflow:flow-…. bypassPermissions lets the headless run edit and commit in the scratch repository without prompting. Host: 2.1.319 (Claude Code).

Output is stdout as printed. Claude Code prints Markdown as plain text in this mode, and a run that waited on a subagent printed a progress line or two before its summary. The only edits are path substitutions: the checkout path is shown as <devflow-checkout> and the home directory as ~. Two /flow-status runs are left out: the one between steps 06 and 07 misreported which DevFlow build was loaded, and the one after step 08 repeated that step's summary. The step 09 timing was run by the operator, not by DevFlow.

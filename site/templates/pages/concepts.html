03/Concepts

How DevFlow works

Six ideas carry the whole system. Each section ends with the page in the repository that defines it, which is the authority if the two ever disagree.

01State lives on disk, not in chat

Everything DevFlow knows is in .planning/: requirements, roadmap, architecture constraints, per-phase plans and summaries, the verifier's report, and STATE.md. Every skill reads STATE.md first, so a new session resumes cold with nothing lost. State files have hard size caps and their sections are rewritten in place, so they stay small enough to load every time.

ARCHITECTURE.md records your stack at major versions, what is forbidden, and your principles. Planners, executors and researchers treat it as law. Anything outside it becomes a decision for you.

That is also why you don't need /clear between steps. Each command loads a few thousand tokens, heavy work runs in fresh-context subagents, and clearing only costs you the conversation, not the project.

Defined in execution-model.md → State and autonomy.md → Session hygiene.

02Plans run in waves

A phase's plans form a dependency graph. An edge exists only where one plan consumes another's output. Waves are the graph's parallel layers, and plans in the same wave share no files and no mutable resources.

Before any executor starts, a deterministic lint checks that the graph is sound and every declared path exists or is declared new. /flow-execute then runs one fresh-context executor per plan, each in its own git worktree, lands their commits on the feature branch one plan at a time, and re-runs each plan's verify on the combined tree. A fan-in guard counts results against spawns, so an executor that died cannot pass for a finished one.

Every phase must also pass one end-to-end smoke command declared in ARCHITECTURE.md, so phase 5 cannot quietly break phase 2.

Defined in execution-model.md → Graph execution and plan-format.md.

03The verifier abstains instead of guessing

A separate verifier, never the executors that did the work, checks the phase's must_haves against anchors: commands it actually ran, tests that actually passed, code it traced. must_haves freeze when execution starts, and a gap closes by changing code, never by weakening the truth.

Some truths are ones the requirements never settled. The planner marks them as backstop truths. For each, the verifier asks one question: does a test or an observed behavior pin the answer? If not, it does not certify it and does not call it a defect. It sends it to you as a human check with a specific ask: write a test that fixes the behavior, or state the rule.

Defined in verification.md.

04Human gates never auto-proceed

A fixed list of decisions always stops for a person, even under /goal or /loop. It covers checkpoint decisions, a secret-scan hit, a new or major-changed dependency, anything outward-facing such as opening a pull request or posting to someone else's, accepting a known defect, and anything destructive in git. Merging is always a person's call.

When a gate is raised, DevFlow writes a ## Gate block to STATE.md with the question, the options and their consequences, so a driver can show the choice without parsing prose. When it is answered, the answer, the git identity and the SHA go into the append-only DECISIONS.md, in the same commit as the work it approved.

Some skills go further: /flow-release, /flow-undo, /flow-hooks and the other outward or destructive ones are explicit-only, so the host will not let the model start them at all.

The authoritative list is in autonomy.md. Overview in docs/autonomy.md.

05One status line drives autonomy

Every skill ends with FLOW: CONTINUE|GATE|BLOCKED|DONE | position | next: command. /flow-next advances exactly one step and prints that line. Claude Code's /goal keeps calling it while the answer is CONTINUE:

/goal FLOW says DONE, GATE, or BLOCKED, or stop after 40 turns
/flow-next

Loop rails stop a run that is going nowhere: a stuck detector on what the routing matched, an iteration cap, and an optional wall-clock cap, tuned in .planning/config.json. A counter that cannot be read is BLOCKED, never zero.

Defined in docs/autonomy.md.

06Providers and model tiers

DevFlow runs as skills inside the host you already use. By default every role runs as that host's native subagent. A delegating skill accepts --provider native|claude|codex, and a project can save the choice as agents.provider in .planning/config.json, with the flag winning. Sending a role to the other provider needs both CLIs installed and signed in, and keeps every checkpoint, branch rule and secret scan.

Each role declares its model. Judgment roles run on the top tier. Bounded roles, including the high-volume executor, run a tier down, which is safe because a DevFlow plan is a complete, unambiguous prompt for the executor. You can override any role in config.json.

Defined in docs/providers.md and hosts.md.

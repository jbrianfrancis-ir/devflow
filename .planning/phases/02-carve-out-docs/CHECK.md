## New findings

1. **all five plans | `must_haves.truths`, the D-14 truth | the `r+d == 1` invariant produces false
   violations on correct work.** D-14's actual invariant is *the prose is in exactly one of the two
   files*; `r` and `d` are `grep -c` **line** counts, so the sum is only 1 when the anchor also
   occupies exactly one line on each side. `mapped_sha` — an anchor 02-02 uses — already appears
   **twice on README line 116** ("carries a `mapped_sha`" and "diff `mapped_sha..HEAD`", two
   different sentences). If the executor writes the page one sentence per line, an entirely correct
   move reads `README=0 PAGE=2` and the truth goes red. Demonstrated on a repo whose move is
   correct:
   ```
   README mapped_sha lines: 0     page mapped_sha lines: 2
   D-14 VIOLATION 691de9e5… [mapped_sha] README=0 PAGE=2      <- FALSE POSITIVE
   ```
   The same fires for any anchor an executor puts in a sub-heading as well as in prose —
   `Environment manifest` and `Sweep the fleet` are the obvious candidates, and the plans explicitly
   instruct "add sub-headings". A truth that can go red on correct work is worse than no truth,
   because `must_haves` are frozen once execution starts: the executor's only sanctioned move is to
   change the page, and the page is right. **Fix:** replace `[ $((r+d)) = 1 ]` with a test that
   exactly one side is non-zero —
   `{ [ "$r" -eq 0 ] && [ "$d" -gt 0 ]; } || { [ "$r" -gt 0 ] && [ "$d" -eq 0 ]; }`.
   Verified against every scenario: S1 silent, S2 still caught (3 violations), S3 still caught, and
   the `mapped_sha` false positive gone.

2. **all five plans | `must_haves.truths`, the D-14 truth | empty commit set passes silently.**
   `for sha in $(git log --format=%H --grep 'DevFlow-Plan: 02-NN')` iterates zero times if no commit
   carries the trailer, and a zero-iteration loop prints nothing — which this truth reads as PASS.
   Nothing in `must_haves` asserts the trailer is present, so a single mistyped or forgotten trailer
   silently re-opens exactly the window round 1's issue 1 was raised to close. Demonstrated: the same
   copy-without-removal violation as S2, committed **without** the trailer, produced no output at all.
   **Fix:** guard the enumeration —
   `shas=$(git log --format=%H --grep 'DevFlow-Plan: 02-NN'); [ -n "$shas" ] || echo "D-14 UNPROVEN: no commit carries DevFlow-Plan: 02-NN"; for sha in $shas; do …`.
   Verified: the untrailered scenario now prints `D-14 UNPROVEN: no commit carries DevFlow-Plan: 02-01`
   and the three passing scenarios are unaffected.

3. **02-05 | Task 1 `<verify>` | the heading loop exits non-zero when it passes.**
   `for h in '^## Autonomous operation' '^## Session hygiene'; do grep -q "$h" README.md && echo "STILL PRESENT: $h"; done`
   takes its exit status from the last iteration, and on success the last `grep -q` fails, so the
   loop exits 1 with empty output. Measured: `output=[]  exit=1`. A verifier grading on exit status
   records a phantom failure on a correct README. **Fix:** invert to the same shape the other plans
   use — `for h in …; do ! grep -q "$h" README.md || echo "STILL PRESENT: $h"; done` — or state in
   the `<verify>` that the check is the *output*, not the status.

4. **02-01 through 02-05 | `<verify>` blocks and 02-01's first truth | the `<anchor>` substitution
   template breaks on two anchors.** The instruction "for each of the anchors: `grep -c '<anchor>'
   README.md`" cannot be followed literally for `doesn't also get to rule` (02-04) or
   `isn't decomposition` (02-04): substituted into single quotes the apostrophe terminates the
   string. The planner solved this correctly inside the D-14 command (those two pairs are
   double-quoted there) but the verify templates were not updated to match. Loud rather than silent —
   the executor gets a syntax error, not a wrong answer — but it is friction in the one place the
   plans promise an executor with no memory of this conversation can run. Pre-existing rather than
   introduced by the revision. **Fix:** write the template as `grep -cF "<anchor>" README.md`.

5. **MAPPING.md | G3 | the fence toggle can invert, and misses tab-indented fences.** Two small
   divergences from `_code_fence_mask`. (a) The checker requires a closer of the *same* character;
   G3's awk toggles on any fence-shaped line, so a `~~~` line inside a ` ``` ` block flips the state
   and every subsequent fence boundary is inverted — prose gets scanned (noisy false positives) and
   fenced content gets skipped (fail-open). (b) The checker `strip()`s before matching, so a
   tab-indented fence *is* masked; G3's `^ *` matches spaces only, so a tab-indented fence is
   invisible to the guard. Neither is reachable from the content this phase moves — no page it
   writes contains a fence of either character — so this is a hardening note, not a blocker.
   **Fix if cheap:** `/^[ \t]*(```|~~~)/`, and note the same-character closing rule as a known limit.

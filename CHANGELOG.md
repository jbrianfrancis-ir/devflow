## 0.47.0 (2026-11-09)
- Repeated mistakes become checks, not prose: the DevFlow pointer block that `/flow-new` and `/flow-migrate` write into `CLAUDE.md` and `AGENTS.md` (`templates/agent-pointer.md`, and this repo's own copies; existing projects keep their block until it is rewritten) now says a repeated mistake gets a deterministic lint/check whose error explains the fix, not a prose rule. The same rule is applied where DevFlow detects repeats: `flow-verifier` names the lint/check rule that would catch a `[REPEAT]` gap on that gap line in VERIFICATION.md, the `/flow-execute` repeat GATE recommends it instead of another LEARNINGS bullet, and `/flow-debug` step 3 adds one in the fix commit (existing lint or test tooling, shown failing on the original mistake) when a root cause repeats a mistake LEARNINGS.md already records, instead of another LEARNINGS bullet (when existing tooling cannot express it, the bullet stays and Resolution says why). Prompt text only; no new script, hook or gate.


## 0.46.0 (2026-11-08)
- Incident intake: `/flow-debug --incident` (investigate now) or `/flow-todo --incident` (handle later) takes a production alert as pasted text or ServiceMonitor output, an App Insights or incident link, or both, and opens the next cycle through new `plugins/devflow/scripts/flow-incident.py`. It writes one `.planning/incidents/<id>.md` record plus a debug session (`--route debug`) or one TODOS.md line (`--route todo`); the route is required, never inferred. Pasted text is untrusted data: passed only as a file, never through a shell, control characters stripped, secret-shaped values redacted (including `?code=`/`&key=` query values, URI passwords and spaced labels like `API Key:`), stored in a fence it cannot close. Links are passed as a file too (`--link-file`; shell metacharacters refused), recorded, and never fetched. Release attribution reads only existing records (`release-*` tags and the PIPELINE.md prod row from `/flow-release`, SIGNOFF.md and its git history from `/flow-uat`, first-parent PR numbers) against the `--version` or `--at` the alert states. The result is `attributed`, `ambiguous` (every candidate listed; a release dated within a day of the incident has unknown order) or `unattributed` with the reason. It names the release deployed at the time, never a cause, and never assumes the newest release. A repeat intake of the same incident (content hash or `--id`) adds nothing while its entry is open. After the debug session is resolved or the todo checked off, the same alert opens a new entry marked as a recurrence and attributed afresh. It never commits, tags, deploys or touches a gate file.

## 0.45.0 (2026-11-07)
- Opt-in usage report (`"usage_report": true` in `.planning/config.json`; off by default, and off changes no output). Every value is labelled transcribed, not verified: the orchestrator copies it from the Agent tool's `<usage>` or the bridge's new `usage` object (numbers and enums only: claude-peer tokens are `modelUsage` summed over every model, codex-peer tokens `unknown`, duration the bridge's wall clock, `outcome` the status it emitted; failed and timed-out attempts are kept). New `plugins/devflow/scripts/flow-usage.py record` is the only writer — it validates the record, refuses any `n` but the unit's next (a repeated step never double-counts), and with `--content` replaces a VERIFICATION.md while carrying earlier verifier records forward (used by both `/flow-execute` step 4 and `/flow-verify`). `/flow-execute` records executor dispatches right after each `wave-end` (lite: after each plan), committed as `chore(flow): NN usage`, so a gaps stop no longer drops them. The report renders every bridge role for every phase dir, planned-but-unexecuted ones included: executor and verifier with `Coverage k/n recorded` on every row plus an all-`unknown` `not recorded` row and footer for each plan with no SUMMARY or no `usage` line; every other role `not instrumented`. Outcomes are counted as observed (`completed`/`checkpoint`/`failed`/`unknown`) instead of a retry label; the model column is the requested model; tokens are never summed across sources; `partial: N (k/n known)` marks a sum with gaps. No savings or plan-percentage figures; no prompt or message text is recorded.
